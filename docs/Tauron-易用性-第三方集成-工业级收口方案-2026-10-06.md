# Tauron 易用性 · 第三方快速集成 · 工业级收口方案

> 生成日期：2026-10-06
> 输入基线：`main @ 82ed5e8`（round 69），workspace 版本 `1.1.0`（registry `1.0.2`，tag 落后 HEAD 26 commit）
> 输入文档：《Tauron-独立审计与重构方案-2026-10-06》（下称"独立审计"）、《TAURON-FULL-AUDIT-AND-OPTIMIZATION-PLAN》（Phase A–H 早期草稿，已并入《统一开发计划》，round 69 起不再单列）、《Tauron-Architecture-Competitive-Analysis-Optimization-Plan-V5》
> 本方案定位：**在既有 R0–R5 重构路线之上，补一整条"接入方视角"的主线**——易用性（DX）、第三方快速集成（TTV）、工业级交付证明。与 R0–R5 的关系：不替代、不冲突，而是给它们排"对外价值"的序：先让外部开发者装得上、跑得通、看得懂，再谈重构深度。

## 0. 为什么需要这份方案

三份既有审计共同指向一个结论：

> **治理底座（命令层/生命周期/授权/设置/恢复/审计）是扎实的，但从"外部接入方"的视角看，今天没有一个 15 分钟内能跑通的完整体验。**

具体断点（全部来自独立审计实测）：

| # | 接入方视角的断点 | 证据锚点 |
|---|---|---|
| B-1 | **装到的 1.0.2 ≠ 仓库的 1.1.0**，`npm create tauron-app@latest` 生成的工程依赖钉在 CLI 自身版本，源码开发要 `--tauron-path` 且必须先 `pnpm install` + `pnpm -r build` | registry `latest=1.0.2`；`src/framework-version.ts` |
| B-2 | **插件"装完就能用"的链路在框架层不存在**：`PluginDispatcher` 零生产实现（唯一 impl 是 `dispatch.rs:290` 的 `#[cfg(test)]` EchoDispatcher），未装载恒 `SC-9001` | 独立审计 §1.3 链路 A |
| B-3 | **JS 投递 fail-open**：队列收下即 `delivered:true`，不校验有活 webview 消费——接入方会看到"成功"然后干等 pending TTL | `eventbus.rs:1076` |
| B-4 | **插件开发循环断裂**：`tauron plugin dev/test/pack/publish` 四条全部未实现（如实 `success:false`）——写一个插件只能手工起进程手工验证 | `packages/tauron-cli` |
| B-5 | **三个 UI 适配器 reference-only**（vue/svelte 零 importer），唯一示例是 vanilla——React/Vue/Svelte 用户没有可抄的工程 | 独立审计 §4.1-P2-F5；`module-maturity.json` |
| B-6 | **教程与排障缺位**：安装文档 4 层"安装"辨析本身就说明心智负担；错误虽然诚实，但接入方拿到 `SC-9001` / `SANDBOX_UNAVAILABLE` 后**没有一页告诉他们下一步该做什么** | `docs/installation.md` |
| B-7 | **版本三分叉**：repo 1.1.0 / registry 1.0.2 / tag 指向 round13-18 旧树——`version:check` 只查内部一致，抓不到分叉 | 独立审计 §P1-M3 |
| B-8 | **数字口径全面腐烂**：实测 Rust `#[test]` 声明 1715、TS 107 文件，README 徽章/正文/V10/竞品四个数全错——对外可信度的第一道伤 | 独立审计 §P1-M1 |

**结论：对第三方而言，当前最大的障碍不是功能缺口，而是"从 `pnpm add` 到看见插件真实跑起来"这条路径上每一环都有摩擦。** 本方案的全部内容就是消除这些摩擦，并配上工业级的交付证明。

## 1. 对标：顶级开源项目的集成体验长什么样

选取四个与 tauron 定位相关的参照系，提取它们被验证过的 DX 模式：

### 1.1 Tauri 2（同生态，直接对标）

| 模式 | Tauri 的做法 | tauron 现状 | 差距 |
|---|---|---|---|
| 一键脚手架 | `npm create tauri-app@latest`：**选框架即出可跑工程**，官方维护 8+ 前端模板，图标用 CLI 真生成（`tauri icon`） | `create-tauron-app` 已有，但**图标是纯色占位图**（`cargo check` 依赖它存在）、无 `tauron icon` 等价物、模板只有 4 框架且仓内零示例 | 中 |
| 安装即用 | `.plugin(tauri_plugin_xxx::init())` 一行，插件自带 permissions/ 自动注册 capability | 应用层接近（`state_init_with_adapter_config` + handler 宏），但**框架层装载后恒 `SC-9001`** | **大** |
| 排障命令 | `tauri doctor` / `tauri info` 输出环境诊断，可直接贴 issue | `tauron doctor` 真探测环境 ✅，但**不输出可粘贴的版本/feature 矩阵摘要**，错误码没有"下一步"指引 | 中 |
| 版本纪律 | CLI 与框架版本解耦明确，移动端模板同步发 | **1.1.0 未发 + tag 指旧树 + registry 落后** | **大** |

### 1.2 VS Code Extension Host（插件平台的黄金标准）

| 模式 | 做法 | tauron 对应缺口 |
|---|---|---|
| 插件开发闭环 | `yo code` 生成 → `F5` 调试宿主 → 断点进插件 → 发布 `vsce package/publish` 全链路工具化 | `plugin dev/test/pack/publish` **四条全未实现**；没有调试宿主 |
| 激活模型 | `activationEvents` 声明式延迟激活 | 无（Manifest V3 计划内） |
| API 稳定性分层 | `proposed` → `stable` API 版本化， proposing API 有 expire 机制 | 无 API 版本域（V5 §40 已识别） |
| 文档站 | code.visualstudio.com API reference 自动生成 | **无 API reference 生成物**，docs 是架构叙事文 |

### 1.3 Extism（WASM 插件运行时的集成极简主义）

| 模式 | 做法 | 借鉴点 |
|---|---|---|
| host 接入 | `Plugin::new(wasm, [])` 两参数起一个插件；多语言 host SDK（Go/Rust/Python/Node…） | tauron 的 WASM 引擎真（wasmi）但 **ABI 停在 `(i64,i64)->i64`，JSON↔线性内存 ABI 未实现**（独立审计 §1.2），投递恒 `delivered:false` |
| 插件 SDK | PDK 多语言（Rust/Go/JS/Python…），`npx extism init` 脚手架 | tauron 的 plugin-sdk 只覆盖 TS 侧 |
| host functions | 声明即用，自动桥接 | tauron 的 host_fn 白名单有配置无执行接线 |

### 1.4 Electron Forge（打包发布链路）

| 模式 | 做法 | 借鉴点 |
|---|---|---|
| 打包 | `forge package` 一条命令产出全平台包 | tauron release.yml 有 CI 但**无本地可复现的打包命令** |
| 自定义模板 | template 机制允许社区贡献工程模板 | create-tauron-app 模板硬编码在 CLI 内 |

### 1.5 提炼出的五条通用定律

1. **TTV（time-to-value）≤ 15 分钟**：从 `npm create` 到看见自己的改动生效，中途不允许出现"需要读架构文档才能继续"的断点。
2. **错误即路标**：每个错误码后面跟"下一步动作"（文档锚点 / 修复命令），而不是只有诚实。
3. **默认值即生产值**：默认装配应该就是安全且可用的；unsafe 才需要 opt-in，而不是"可用"需要 opt-in。
4. **示例即文档**：每个公开能力至少一个仓内可运行示例；reference-only 的包等于没有。
5. **版本即承诺**：tag、registry、repo 三处一致是最低门槛；协议/SDK 版本域独立于包版本。

## 2. 目标与总原则

### 2.1 三大目标（可度量）

| 目标 | 度量 | 当前 | 目标值 |
|---|---|---|---|
| **T1 快速集成** | 从 `npm create tauron-app` 到"自己的第一个插件方法被真实调用并返回"，允许的最长步骤数与外部前置知识 | 装到 1.0.2；插件链路框架层 ❌；JS 投递不诚实 | **≤ 5 步、≤ 15 分钟、零架构文档前置** |
| **T2 易用性** | 插件开发闭环命令数（new → dev 调试 → test → pack） | 4 条中 0 条实现 | **4 条全部可用 + 热重载** |
| **T3 工业级** | 发布证据完备度（版本一致性、E2E、SBOM、conformance kit、API 稳定性域） | 版本三分叉；无 packaged E2E；无 conformance kit | **tag=registry=repo；三形态 Runtime Conformance；公开 Conformance Kit** |

### 2.2 五条不可违背原则（继承自独立审计 §5.0，并扩展）

1. **诚实纪律只增不减**——所有易用性改进不得以伪造成功换取流畅（这是本仓核心资产）。
2. **易用性修复优先发生在"默认装配"里**——不让接入方为了可用性去开 feature flag；unsafe/重依赖才 opt-in。
3. **每个新门禁必须带 `--self-test`**——独立审计已证明文本针门可被改名绕过（§P1-M4）。
4. **文档数字一律来自构建产出**（`contracts/facts.json`），手写数字即 bug。
5. **占位必须有归宿**——继承独立审计原则 2：本方案新增的任何占位（如 Rust 插件执行器）都必须排进转正或删除批次。

## 3. 易用性改进方案（DX-1 ~ DX-8）

### DX-1：修复"接入第一分钟"——版本与脚手架收口【P0，天级】

**问题**（B-1 / B-7 / B-8）：接入方第一分钟就撞上"装到的和读到的不是同一个东西"。

**方案**：

1. **发布 1.1.0（或重切 tag 为 `v1.1.1-rc` 并发布 1.1.1）**：结束"1.1.0 未发 + tag 指向 round13-18 旧树"双坑。发布前跑 `publish-npm.mjs --check`（20/20）与 `publish-crates.mjs --check`（16 crate，含漏发的 `tauron-ffi`——1.0.2 时代漏发，无 `publish = false`，必须在本次补发）。
2. **`version:check` 增加 tag/registry 维度**：当前只校内部一致（独立审计 §P1-M3）；新增"tag == HEAD 树"与"registry 目标版本 == 根版本"两个判定，分叉即红。
3. **`contracts/facts.json` 单一数字真源**：CI 中由 `cargo test` 汇总 + grep 生成测试数/命令数（85=61+22+2）/包数/crate 数；README 徽章与所有文档读取该文件。即刻修正为实测值：Rust 声明 **1715**、TS **107** 文件/20 包。
4. **脚手架图标真生成**：`tauron-app new` / `create-tauron-app` 内置 SVG→PNG/ICO/ICNS 转换（纯 Rust 依赖如 `image` + `ico`，或内置占位 SVG 品牌字），消除"发布前须手工换图标否则 `cargo check` 都过不去"的坑；同时提供 `tauron-app icon <png>` 子命令（对标 `tauri icon`）。
5. **CLI 版本策略**：脚手架生成的依赖不再钉 CLI 自身版本，而是钉"当前 stable registry 版本"（读 npm dist-tags），`--tauron-path` 继续覆盖源码开发。

**验收**：新机器上 `npm create tauron-app@latest -- ./x --framework react && cd x && npm i && npm run tauri dev` 在不读任何架构文档的情况下编译通过并弹窗；`pnpm version:check` 能抓 tag 分叉。

### DX-2：补齐插件开发闭环——`plugin dev/test/pack` 转正【P0，1–2 轮】

**问题**（B-4）：插件作者的四条核心命令全部未实现。没有开发循环就没有插件生态，这是 T2 的全部内容。

**方案**（按价值/成本排序，继承独立审计 R0 的"占位转正"纪律）：

1. **`tauron plugin dev`（最高优先）**：
   - 以 `examples/minimal-app` 为**调试宿主**（debug host）：`plugin dev` 起一个 vite dev server + 启动调试宿主（`tauri dev`）并注入当前插件目录为 dev 插件源；
   - **热重载**：监听插件源码变更 → 经 `host_registry_admin` 热禁用 → 重载资产 → 热启用（复用既有 10 态状态机的 `DISABLED→ENABLED` 转移，不新造机制）；
   - DevTools：宿主 webview 开 devtools，`plugin dev` 端打印插件侧 `console` 桥接输出。
2. **`tauron plugin test`**：跑插件自带的 vitest 用例（脚手架 `plugin new` 已生成测试骨架），接入 `@tauron/app-contract-kit` 的 `MockBackend`；对 Process 型插件走 `tauron-test-sidecar` 同款帧回路。
3. **`tauron plugin pack`**：产出 `.tpkg`（zip 净化常量直接复用 `tauron-market::validate_zip_constants`，即轮 65 已对齐的 200 MiB/100 MiB 预算），附 manifest 校验（复用 `tauron-host::manifest`）。
4. **`tauron plugin publish`**：保持未实现但把 `success:false` 的输出升级为**路标**：打印"发布需要 registry 后端，当前可用 `plugin pack` + 手动分发；registry 协议见 docs/…"（对应 §5-D7）。
5. **`tauron plugin sign` 从摘要升级为真签名**：当前是真 SHA-256 摘要 + `simulated:true`（`plugin-lifecycle.ts:157`）。升级为 Ed25519（复用 `@tauron/market` 的密钥对 API），`simulated` 落为 false——这是把"诚实占位转正"的第一示范。

**验收**：`tauron plugin new demo --type js && cd demo && tauron plugin dev` → 调试宿主弹窗加载该插件 → 改插件代码 → 2 秒内界面热更新；`tauron plugin test` 真跑用例并如实报数；`tauron plugin pack` 产出的 `.tpkg` 能被 `host_registry_install`（开 `plugin-install` feature 的宿主）安装并通过验签。

### DX-3：错误即路标——错误码的"下一步"体系【P1，0.5 轮】

**问题**（B-6）：诚实但无助。接入方拿到 `SC-9001` 不知道要装载 dispatcher；拿到 `SANDBOX_UNAVAILABLE` 不知道 dual-world 是占位。

**方案**：

1. **错误码注册表扩展**：`contracts/error/error-codes.json`（已有）为每个码增加 `recovery` 字段——一句话下一步 + 文档锚点。示例：
   - `SC-9001`：`"未装载 PluginDispatcher。应用层接入请改用 tauron_adapter 装配（docs/integration/incremental-adoption.md）；框架层接入需自实现并装载 dispatcher（docs/api/plugin-dispatcher.md）"`
   - `E_PLUGIN_TYPE_NO_RUNTIME`：`"Rust/Wasm 形态暂无运行时。改用 Js/Process，或等待 RuntimeDriver 统一（roadmap）"`
   - `SANDBOX_UNAVAILABLE`：`"dual-world 为占位。插件 UI 请走 host_window_create + PluginBridge"`
2. **Rust 错误实现同步**：`error.rs` 的 `Display` 输出带 `hint:` 段；wire-gate 增加"每个有 `recovery` 字段的码，Rust Display 必须包含同义提示"的断言。
3. **TS 侧 `formatTauronError(err)` 工具**：输出 `code / message / hint / docLink` 四段，React/Vue/Svelte 适配器默认用它格式化 `useInvoke` 的错误态。

**验收**：wire-gate 断言 100% 覆盖；`docs/api/error-codes.md` 从 JSON 生成（纳入 `command-surface:gen` 同款"生成物 + CI 复算"机制）。

### DX-4：示例矩阵——消灭 reference-only【P1，1 轮】

**问题**（B-5）：React/Vue/Svelte 适配器零仓内消费者；唯一示例 vanilla。reference-only 的包在台账上被如实标注，但对外等于不可用。

**方案**：

1. `examples/` 扩为矩阵（每个都真装配、CI 编译、README 三步可跑）：

```
examples/
├── minimal-app/            # 现有：vanilla，最薄底座
├── react-host/            # React + useInvoke/useEvent + 插件面板窗
├── vue-host/              # Vue composables 同款
├── svelte-host/           # Svelte stores 同款
├── plugin-js-quickstart/  # 插件作者视角：tauron plugin new 产物 + dev 循环演示
├── plugin-process-sidecar/ # Process 插件：真子进程 + 崩溃重启
└── embedded-substrate/    # 只取底座 61 命令的宿主（substrate-only feature）
```

2. **CI 接线**：每个 example 进 `ci.yml` 的 `cargo check` 矩阵（minimal-app 已有先例），React/Vue/Svelte 三个再跑 `pnpm build`——这一步同时把三个适配器从 `reference-only` 改判 `repo-consumed`，`module-maturity.json` 与 wire-gate 的 `consumerStatus` 门禁同轮更新。
3. **Playground（进阶，P2）**：`examples/playground/`——一个内置插件管理器 UI 的演示宿主，装/卸/启/停/授权审批全走真实命令，作为"活文档"。

**验收**：`module-maturity.json` 中 `adapter-react/vue/svelte` 的 `consumerStatus` 全部改判 `repo-consumed`；每个 example 的 README 遵循"三条命令内可跑"模板。

### DX-5：文档站与分层文档体系【P1，1 轮 + 持续】

**问题**：docs/ 是给维护者看的架构叙事（6 份重叠方案 + 488KB 台账），没有给接入方的分层文档。独立审计 §3 根因 4 已诊断"文档增长快于数字同步"。

**方案**：

1. **文档分三轨**（结构上物理分开）：
   - `docs/getting-started/`——接入方轨道：安装（5 分钟）→ 第一个插件调用（15 分钟）→ 第一个插件开发（30 分钟）→ 发布。每篇 ≤ 300 行、零架构术语、命令可复制。
   - `docs/guides/`——插件作者轨道：权限/事件/生命周期/Process/Wasm/打包签名/调试。
   - `docs/architecture/` + `docs/archive/`——维护者轨道：现有 6 份方案收敛为一份"当前状态 + 开放项"活文档（独立审计 R5 的方案，此处采纳为前置）。
2. **API reference 生成**：TS 侧 `api-extractor` / typedoc 产出 `docs/api/`；Rust 侧留给 docs.rs（Cargo.toml 已刻意不设 `documentation`）。命令面参考已生成（`command-surface:gen`），错误码表随 DX-3 一并生成。
3. **版本化文档**：文档站按 npm 版本分档（`/v1/`），1.1.0 的特性描述只出现在 v1 档——配合 DX-1 的版本收口。
4. **文档门禁扩展**：`check-doc-line-refs.mjs` 白名单纳入 getting-started/guides 全部文件（当前只 7 白名单 283 引用，方案文档不覆盖——独立审计 §P1-M2）。

**验收**：外部开发者从 `docs/getting-started/` 走完 T1 目标全程不碰 `docs/architecture/`；`pnpm docs:check` 覆盖新轨道全部行号引用。

### DX-6：TS API 面收敛——21 包 → 15 包【P1，1 轮，对齐独立审计 R2.5】

**问题**：21 个 npm 包里 `dual-world`/`shell-matrix` 零消费者、`@tauron/core` 死导出面、三适配器分立——接入方面对的安装决策面过大。

**方案**（采纳独立审计 R2.5 并按 DX 视角细化）：

1. 三适配器合并为 `@tauron/adapter`（子路径导出 `@tauron/adapter/react|vue|svelte`），旧包名保留一个 deprecation 周期转发；
2. `dual-world` / `shell-matrix` 转 `private: true` + 从 README 特性表移除（保留代码与测试，等真引擎接入再回公开面）——**这不是删功能，是把"占位不该出现在货架"制度化**；
3. `@tauron/core` 死导出按孤儿台账三选一处理（独立审计 R0 已列）；核心编排 API 明确 deprecation 路径：`invokePlugin`/`listenEvent` 迁到 `@tauron/host`，core 转兼容包；
4. **接入方最终只需要认识 3 个包**：`@tauron/host`（宿主）、`@tauron/plugin-sdk`（插件）、`@tauron/adapter/react`（框架绑定）——写进 getting-started 第一段。

**验收**：公开 npm 包 20 → 15；`pnpm publish:npm -- --check` 全绿；deprecation 警告在旧包 install 时可见。

### DX-7：CLI 体验统一——`tauron doctor` 升级 + `tauron info`【P2，0.5 轮】

1. `tauron doctor` 输出末尾追加**可粘贴环境摘要**（对标 `tauri info`）：OS/Rust/Node/tauron 版本/registry 版本/feature 矩阵/宿主装配档位——用户可直接贴 issue；
2. `doctor` 检查项新增：CLI 版本 vs registry stable 的偏斜警告（"你用的是源码 1.1.0，npm stable 是 1.0.2，注意差异"）；
3. `tauron-app init`（注入式接入）在检测到既有 `.invoke_handler` 时，除了非零退出（现状），**打印精确的合并 diff 建议**。

### DX-8：能力协商前置到开发期【P2，0.5 轮】

`host_capabilities` 运行期协商已有；补开发期版本：
- `@tauron/host` 的 `HostClient` 初始化时拉取能力并缓存（V5 §S6 已设计，本方案纳入排期）；
- 脚手架生成的 capability 模板三档（V4-S5）随 `tauron-app new` 落盘，接入方不用手写 JSON；
- VS Code 式"建议插件"：`PluginManagerStore` 遇到未装配域（`host_capabilities.unsupported`）时 UI 给出降级提示而非空白。

## 4. 第三方快速集成方案（INT-1 ~ INT-5）

### INT-1：框架层 PluginDispatcher 生产实现——"两层可分开取用"兑现【P0，2 轮】

**问题**（B-2，独立审计 P0-F2/P0-F1）：宣称"只要信封协议就接框架层"，但接入方必须自实现 dispatcher，仓库内只有测试用 EchoDispatcher。这是 T1 路径上最大的名不副实点。

**方案**（采纳独立审计 R1.5 的"收敛"路线并细化接入面）：

1. **生产 `AppLayerDispatcher`**：`tauron-adapter` 提供一个实现 `tauron_shell::PluginDispatcher` 的桥——把框架层信封 `plugin_invoke` 委托给 canonical 的 `tauron-host` 调用链（registry → authz → call_delivery → settle）。**一次装载，框架层三命令即刻可用**：

```rust
// 框架层接入方的最终形态：
tauri::Builder::default()
    .plugin(tauron_shell::commands::state_init())
    .invoke_handler(tauron_shell::tauron_generate_handler![])
    .setup(|app| {
        // 一行装载生产分发器（新增，取代"必须自己写"）：
        tauron_shell::bridge::mount_app_dispatcher(app.handle(), /* deps */)?;
        Ok(())
    })
```

2. **删除并行的 legacy registry/eventbus/config**（`tauron-shell` 内自标 legacy 的那套）——框架层变成"协议 + 类型 + serde 门面 + 委托桥"的单一真源，`ConfigLayer`/内层 ACL 要么接进 `handle_invoke` 要么移出特性表（独立审计 R1.5 原文要求）；
3. **E2E 门禁**：`plugin_invoke` → dispatcher 桥 → JS 插件真实调用 → settle，一条仓内测试锁定；`SC-9001` 只允许出现在"未装载且宿主显式选择裸壳"的场景。

**验收**：getting-started 的"框架层接入"章节从"你必须自己实现 dispatcher"改写为"一行 mount"；wire-gate 钉住桥的存在与 E2E。

### INT-2：JS 投递诚实化 + 默认装配可用化【P0，0.5 轮】

**问题**（B-3，独立审计 P0-I1）：`eventbus.rs:1076` 队列收下即 `delivered:true`——fail-open 与本仓纪律直接冲突，且是接入方最常见的"看起来成功实则挂死"。

**方案**（采纳独立审计 R1.1）：

1. `delivered:true` 前置条件 = 目标插件的入站泵已注册或窗已 bootstrap（对齐 `process_delivery.rs:141` 的 `live_runtime` 检查）；否则 `delivered:false` → `E_PLUGIN_TYPE_NO_RUNTIME`；
2. E2E：关窗后调用不得报 delivered（pending TTL 内返回明确错误而非超时）；
3. **`simulated-never-commits` 门禁作用域从 6 文件扩到全仓**（独立审计 §P1-M4：文本针门作用域窄）——这是把"局部诚实"升级为"全局诚实"的第一步，配合 `--self-test` 全覆盖。

### INT-3：Conformance Kit 公开化——让接入方能自证【P1，1 轮】

**问题**：T3 的核心缺口之一。外部宿主（自实现 HostTransport 的接入方）没有任何方式验证自己的实现符合契约。

**方案**：

1. `@tauron/conformance-kit`（新公开包）：从 `@tauron/contract-tests`（私有）提取可对外执行的面——传入一个 `Backend` 实现，跑 130+ wire 断言 + 生命周期 + 错误码映射 + 流控序列（`CreditWindow` 的四条宿主用例序列已存在，轮 66）；
2. Rust 侧 `tauron-conformance`（或 feature）：宿主侧 `SubstrateState` 装配的自测库——`production_doctor` 已有基础，扩展为可编程断言集；
3. **版本兼容声明**：conformance kit 自带 `protocolVersion`，N-1 原则（V5 §40）的第一落点——kit 1.x 能测 host 1.x 与 2.x；
4. 文档：接入方指南新增"自测你的 HostTransport/Backend"章节。

**验收**：`MemoryTransport` 跑通全量 conformance（这也补上独立审计发现的"MemoryTransport 无流式内核无取件泵"缺口——做 kit 时必须先修它，一举两得）。

### INT-4：Runtime 统一——JS/Process/WASM 同一份契约【P0，2–3 轮，对齐 V5 Phase B / 独立审计 R1.2–R1.4】

这是"插件系统题眼闭合"的主战场，直接决定接入方敢不敢把插件当生产能力。排序上采纳独立审计的优先级：

| 批次 | 内容 | 集成视角的产出 |
|---|---|---|
| R1.2a | WASM 线性内存 JSON ABI（替换 `(i64,i64)->i64`） | 插件作者可以用 Rust/AssemblyScript 写 wasm 插件 |
| R1.2b | WASM supervisor 子进程（复用 `tauron-proc` 帧机构 + per-call host_fn 截止） | wasm 插件崩溃不拖垮宿主 |
| R1.3 | Rust 插件执行器：**推荐编译为原生 sidecar 复用 Process 链**（独立审计推荐） | 第三方 Rust 开发者有路径 |
| R1.4 | Process Production 可用：补 Hard 沙箱（landlock/seccomp + Windows restricted token）或显式 `TrustedSigned` 信任档 | 生产环境可用 Process 插件 |

**统一约束**：四形态收敛到单一 `RuntimeDriver` trait（prepare/start/invoke/cancel/health/stop），**同一份 Conformance Kit 对所有形态跑同一用例集**——这也是 INT-3 的内容扩展。

**验收**：`examples/plugin-process-sidecar` 与 wasm 示例在 Production 档默认装配端到端跑通（invoke→settle），CI 四平台矩阵绿。

### INT-5：注入式接入增强——已有 Tauri 项目的迁移路径【P1，0.5 轮】

1. `tauron-app init --dir` 检测既有 `.invoke_handler` 时的**自动合并**：生成合并后的代码片段（当前只报告需手工合并然后退出）；
2. **capability 模板随 init 落盘**（三档，DX-8）；
3. 迁移指南：`docs/guides/migrating-from-tauri-plugin.md`——"你已经用 Tauri plugin 做了 X，怎么换成 tauron 插件获得运行时治理"对照表（这是从 Tauri 生态导流的关键文档）。

## 5. 工业级收口方案（IND-1 ~ IND-5）

### IND-1：版本三域与发布纪律【P0，天级】

（DX-1 的工业化面，此处定纪律）

1. **四个版本域**（采纳 V5 §40）：`HostProtocolVersion` / `ManifestVersion` / `PluginRuntimeABI` / `SDK SemVer`——不得用 npm/crate 版本隐式代替协议版本。落点：manifest 增 `manifestVersion` 字段（Manifest V3 的第一块砖）；
2. **N-1 原则**：HostProtocol 2 的 server 必须支持 client 1/2，unknown command 不得 panic——wire 层已有 extensions 收口（`wire.rs:58-66`），补协议协商命令 `host_protocol_info`（V5 §27 设计已就绪）；
3. **发布节奏**：semver 严格化——1.1.0 发布后，任何公开面破坏性变更必须 2.0；deprecation 至少留一个 minor 周期（DX-6 的适配器合并遵守此纪律）；
4. **tag/registry/repo 三处一致进 CI**（DX-1.2）。

### IND-2：发布证据链【P1，2 轮】

对照独立审计 §P2 与 V5 Phase G，按"接入方可验证"排序：

| 证据 | 现状 | 动作 |
|---|---|---|
| Packaged E2E | ❌ | release.yml 构建后**在三个平台真装一遍**（安装包 → 启动 → 跑 minimal-app 冒烟）再挂 Release |
| SBOM + provenance | ❌ | `cargo cyclonedx` / npm SBOM 进 release 附件；GitHub artifact attestation |
| Reproducible build | ❌ | 同 commit 两次构建字节对比（Rust profile 已 `lto=thin, strip=true`，具备基础） |
| cargo-fuzz | ❌ | 优先靶：`wire.rs` 解析、`envelope.rs` 反序列化、zip 净化、`scoped_fs` 路径——四个安全关键入口 |
| Coverage | ❌ | `cargo llvm-cov` + vitest coverage → 阈值门禁（先基线后阈值，不一步到位） |
| main 分支保护 | ❌（N-23） | ruleset + CODEOWNERS + 全部 CI job required——**文档已承认，纯执行项** |

### IND-3：语义成熟度门禁——"货架规则"制度化【P1，0.5 轮】

把独立审计根因 1（"占位无转正约束"）的解法做成机器规则：

1. `contracts/module-maturity.json` 每个公开包/crate 必须有 `state ∈ {stable, preview, experimental, deprecated}`；
2. **新门禁 `check-shelf-rules`**：`experimental` 的包**不得**出现在 README 特性表、getting-started、脚手架模板依赖里（dual-world/shell-matrix 的公开面移除由此制度化）；
3. **占位转正追踪**：每个 `simulated:true` / 恒 `success:false` 的点位在 `contracts/placeholder-ledger.json` 登记（含登记日期与"转正或删除"批次归属）；超过 2 个 minor 周期未处置的占位，门禁要求维护者在"转正排期/降级 private/删除"三选一并在 ledger 签字——**把"诚实"从静态声明变成有时间维度的承诺**；
4. 全仓 `simulated-never-commits` + `success-requires-effect` 作用域扩展（INT-2.3）+ 所有针门 `--self-test`（独立审计 R0 要求）。

### IND-4：可观测性最小可用【P2，1 轮】

采纳 V5 Phase H 但按工业级最小集裁剪：

1. `tracing` span 覆盖每次 plugin call（trace_id/call_id/principal/plugin_id/runtime_kind/时长/错误码）——**只此一项**先落地，OTel exporter 后置；
2. `host_resource_stats` 扩展 per-plugin 调用量/失败量/pending 峰值（独立审计 M-10 的原始缺口）；
3. 慢查询日志：超过阈值的 invoke 输出结构化警告（接入方排障第一入口）。

### IND-5：外部可信度建设【P2，持续】

1. ** SECURITY.md + threat model**（V5 Phase F-5）：先文档后审计；
2. **至少 3 个真实第三方 Consumer**（V4 2.0 判据）：从 examples 矩阵起步，寻找早期采用者（DX-4 的 playground 是展示橱窗）；
3. **外部安全审计**：在 INT-4（Hard 沙箱）+ IND-2（fuzz）之后排期，审计前自证材料即 IND-2 的证据链。

## 7. 一句话总结

治理底座已经值得被信任，现在缺的是**让外面的人用得上它的那条路**：第一分钟不撞版本分叉、第一个插件 15 分钟跑通、第一次失败能看到下一步、第一次上生产有证据链。本方案与既有 R0–R5 重构共享同一套诚实纪律，但把排期的第一投票权交给接入方——**先止血版本与脚手架（天级）、再补插件开发闭环（T2）、再兑现框架层一行接入（T1）、最后用 Conformance Kit 与发布证据链回答"工业级"（T3）**。其中每一项都不新造并行态，全部复用既有机制（状态机热重载、production doctor、wire-gate、market 验签常量），这正是这套底座最大的红利：**改造成集成体验，大部分时候只是把已经造好的引擎接上方向盘**。
